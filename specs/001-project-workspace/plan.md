# Implementation Plan: Project Workspace

**Branch**: `001-project-workspace` | **Date**: 2026-08-28 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/001-project-workspace/spec.md`

**Note**: This template is filled in by the `/speckit-plan` command; its definition describes the execution workflow.

## Summary

Ship the first Ripple slice: a single-project workspace, seeded in memory, where a team can view
project details (name, target deadline, total estimated effort), a full requirement list, a full
task list, and an overall progress figure, and can create/edit/remove requirements and tasks and
link them to each other. Domain logic (entity CRUD rules, association integrity, progress
calculation) lives in a plain-TypeScript core module with no React dependency, per the project
constitution's Domain Core Independence and Determinism principles, so it can be unit-tested in
isolation and reused unchanged by the later dependency/impact-analysis feature. React owns
rendering and input collection only, holding core-computed state as opaque data.

## Technical Context

**Language/Version**: TypeScript ~6.0 (strict, `verbatimModuleSyntax`), targeting ES2023, on React 19.2

**Primary Dependencies**: React 19 + ReactDOM 19 (existing); Vite 8 (existing, build/dev server).
New dev-only dependencies: Vitest (unit tests) and @testing-library/react + jsdom (light component
tests) — see research.md for rationale.

**Storage**: N/A — all project data (project, requirements, tasks, associations) lives in
in-memory React state for the current browser session only; no persistence layer of any kind.

**Testing**: Vitest for domain-core unit tests (colocated `*.test.ts` next to the code under
`src/core/`); React Testing Library for a small number of workspace interaction smoke tests.

**Target Platform**: Modern desktop web browsers, single-page application, no server component.

**Project Type**: Web — frontend-only single project (existing Vite + React app at repo root;
no backend/API is introduced).

**Performance Goals**: Not a performance-sensitive domain at this scale; all interactions (add,
edit, remove, associate, progress recompute) must feel instantaneous (sub-frame, no visible lag)
against the seeded dataset size described in Scale/Scope below.

**Constraints**: Frontend-only, no backend/database/authentication/external integrations (per
spec and constitution Principle VI); all state must reset on page reload; no new state-management
library.

**Scale/Scope**: Single project; seeded with roughly 5-8 requirements and 15-25 tasks with mixed
statuses and existing associations — enough to make progress and list views meaningful, not a
data-volume concern.

## Constitution Check

*GATE: Must pass before Phase 0 research. Re-check after Phase 1 design.*

| Principle | Status | Notes |
|---|---|---|
| I. Domain Core Independence | PASS | All entity CRUD, association-integrity, and progress-calculation logic lives in `src/core/` as plain TypeScript with no `react`/`react-dom`/DOM imports; React components call into it and hold its output as opaque state. |
| II. Determinism & Reproducibility | PASS | Core operations are pure functions over explicit input state; entity IDs are generated by a deterministic in-core sequence (not `crypto.randomUUID()` or `Date.now()`), so tests can assert exact IDs and exact progress values. See research.md. |
| III. Explicit Dependency Representation | PASS (scoped) | This slice has no task-to-task dependency graph (explicitly out of scope per spec Assumptions). The one relationship it does introduce — requirement↔task association — is modeled as an explicit, typed join record, never inferred from naming or position, consistent with this principle's intent. |
| IV. Explainable Impact Output | N/A for this slice | This feature computes no "impact result"; it only establishes structure and a simple progress figure. Explainability becomes binding once the later impact-analysis feature is planned. |
| V. Test-First for Core Logic | PASS (planned) | Every `src/core/` function (add/edit/remove requirement, add/edit/remove task, associate/unassociate, computeProgress) gets unit tests covering the edge cases enumerated in the spec, written alongside the implementation. |
| VI. Simplicity & Minimal Infrastructure | PASS | In-memory `useState`/`useReducer` only; no state-management library, no router, no backend, no database. Vitest/RTL are added strictly to satisfy Principle V's testing requirement, not general-purpose infrastructure. |

No violations requiring justification — Complexity Tracking table is not applicable.

### Source Code (repository root)

```text
src/
├── core/                       # Domain Core — plain TypeScript, no React/DOM imports
│   ├── types.ts                # Project, Requirement, Task, Association, enums
│   ├── seedData.ts             # deterministic seeded project used on startup
│   ├── ids.ts                  # deterministic ID sequence generator
│   ├── requirementOperations.ts   # add/edit/removeRequirement
│   ├── taskOperations.ts          # add/edit/removeTask, associate/unassociate
│   ├── progress.ts             # computeProgress(project)
│   ├── selectors.ts            # getTasksForRequirement, getRequirementsForTask
│   ├── requirementOperations.test.ts
│   ├── taskOperations.test.ts
│   └── progress.test.ts
├── state/
│   └── useProjectStore.ts      # single hook: React state + dispatch to core operations
├── components/
│   ├── ProjectHeader.tsx       # name, target deadline, estimated effort, progress
│   ├── RequirementList.tsx     # list + add/edit/remove requirement UI
│   ├── TaskList.tsx            # list + add/edit/remove task UI, association controls
│   └── Workspace.tsx           # composes the above into the single workspace view
├── App.tsx                     # replaces current Vite scaffold content
└── main.tsx                    # unchanged entry point

(tests for src/core/* are colocated as *.test.ts next to the code they cover,
matching Vitest's default discovery — no separate tests/ tree is introduced)
```

**Structure Decision**: Single frontend project (this repository's existing Vite + React app at
its root — no backend, no monorepo split). The feature adds one new top-level boundary,
`src/core/`, that must remain free of React/DOM imports per the constitution; `src/state/` is the
thin adapter that lets React consume it; `src/components/` renders it. This directly reuses the
existing `src/`, `App.tsx`, and `main.tsx` rather than introducing a parallel structure.
